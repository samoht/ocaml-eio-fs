# eio-fs

Filesystem helpers and an in-memory [Eio](https://github.com/ocaml-multicore/eio)
backend.

Code written against `Eio.Path` should work the same whether its files live on
a disk or in memory, where a test or a unikernel with no filesystem keeps them.
This library supplies the in-memory backend and the tools around it.
`Eio_fs.Fs.v ()` creates a fresh filesystem in memory, `Eio_fs.Fs.load`
populates it from an existing directory tree, and `Eio_fs.Fs.tree` prints any
`Eio.Path` tree.

The package also ships `Eio_fs.Chaos`, a wrapper that injects faults (short and
torn writes, failed syncs, simulated power loss) into any directory for
crash-consistency tests, and the `eio-fs.sync`, `eio-fs.unix` and `eio-fs.path`
libraries for durable file operations, POSIX-specific calls and lexical path
arithmetic. A torn write commits some of its bytes to the store and then
reports failure. For power loss, `Eio_fs.Chaos.Crash` records every data write
as un-synced until an `Eio.File.sync` on that file makes the earlier writes
durable, and it journals creations, renames, unlinks and the other directory
operations in program order. At a simulated crash, un-synced data writes may be
dropped or reordered, and only a prefix of the uncommitted directory
operations survives, each dropped operation rolled back whole.

## Usage

```ocaml
Eio_main.run @@ fun _env ->
let fs = Eio_fs.Fs.v () in
Eio.Path.save ~create:(`Or_truncate 0o644) Eio.Path.(fs / "hello") "world";
assert (Eio.Path.load Eio.Path.(fs / "hello") = "world")
```

Application code receives an ordinary `Eio.Path` and does not need to know
which backend supplies it, so the in-memory backend serves tests and scratch
filesystems in unikernels alike.

## Embedding a file tree at compile time

The `eio-fs-crunch` binary walks a directory tree and generates an OCaml
module (plus its interface) that embeds every directory, file and symbolic
link, in the style of [ocaml-crunch](https://github.com/mirage/ocaml-crunch).
A dune rule keeps the generated module in sync with the asset directory:

```
(rule
 (targets assets.ml assets.mli)
 (deps
  (source_tree static))
 (action
  (run %{bin:eio-fs-crunch} -o assets.ml static)))
```

The generated `assets.ml` holds the serialised tree as a value of type
`Eio_fs.Crunch.t`; nobody writes entries by hand:

```
(* Generated by eio-fs-crunch. Do not edit. *)

let entries : Eio_fs.Crunch.t =
  Eio_fs.Crunch.
    [
      Dir { path = "/"; perm = 0o755 };
      File
        {
          path = "/index.html";
          perm = 0o644;
          contents = "<h1>Hello from the image</h1>\n";
        };
    ]

let load () = Eio_fs.Crunch.load entries
```

At run time, `Assets.load ()` rebuilds the tree in the in-memory filesystem and
returns its root, so code without a real filesystem, such as a unikernel
or a test, gets an ordinary `Eio.Path` view of its static assets. This
repository crunches [examples/readme/static](examples/readme/static) in exactly
this way, and the example below runs against the generated module:

```ocaml
Eio_main.run @@ fun _env ->
let fs = Assets.load () in
assert (
  Eio.Path.load Eio.Path.(fs / "index.html") = "<h1>Hello from the image</h1>\n")
```
