# eio-fs

Filesystem helpers and an in-memory [Eio](https://github.com/ocaml-multicore/eio)
backend.

A program written against `Eio.Path` should not care whether its files are on
a disk or in memory. Tests often want them in memory, and so does a unikernel,
which has no filesystem at all. This library provides that in-memory backend.
`Eio_fs.Fs.v ()` returns the root of a new, empty filesystem in memory.
`Eio_fs.Fs.load` returns the root of a new one holding a copy of a directory
tree, and `Eio_fs.Path.pp_tree` prints any `Eio.Path` tree. Two of these
filesystems share no file.

For crash-consistency tests, `Eio_fs.Chaos` wraps a directory and injects
faults into it: short writes, torn writes, failed syncs and power loss. A torn
write stores some of its bytes and then reports a failure. To simulate power
loss, `Eio_fs.Chaos.Crash` treats each data write as unsynced until an
`Eio.File.sync` on the same file makes the earlier writes durable. It also
keeps a journal of creations, renames, unlinks and the other directory
operations, in the order the program issued them. When the simulated crash
comes, unsynced data writes may be lost or reordered. Of the directory
operations not yet committed, only a prefix survives, and each lost operation
is undone completely.

Three more libraries come with the package. `eio-fs.sync` has durable file
operations, `eio-fs.unix` the calls that only exist on POSIX systems, and
`eio-fs.path` lexical operations on paths.

## Usage

```ocaml
Eio_main.run @@ fun _env ->
let fs = Eio_fs.Fs.v () in
Eio.Path.save ~create:(`Or_truncate 0o644) Eio.Path.(fs / "hello") "world";
assert (Eio.Path.load Eio.Path.(fs / "hello") = "world")
```

The code that uses `fs` sees an ordinary `Eio.Path`. It cannot tell which
backend is behind it, so the same code runs against a test's in-memory files or
a unikernel's scratch filesystem.

## Testing crash consistency

A test wraps a directory in a crash controller, runs the code under test
through the wrapper, and reads back the image a power cut at that point would
leave. Here a file published with `Eio_fs_sync.save`, which syncs it and its
directory, survives the cut, and one written with no sync is lost:

```ocaml
Eio_main.run @@ fun _env ->
let module Crash = Eio_fs.Chaos.Crash in
let ctl = Crash.v () in
let fs = Crash.wrap ctl (Eio_fs.Fs.v ()) in
Eio_fs_sync.save Eio.Path.(fs / "state") "committed";
Eio.Path.save ~create:(`Exclusive 0o644) Eio.Path.(fs / "draft") "unsynced";
let after = Crash.post_crash ctl in
assert (Eio.Path.load Eio.Path.(after / "state") = "committed");
assert (Eio.Path.kind ~follow:false Eio.Path.(after / "draft") = `Not_found)
```

## Embedding a file tree at compile time

The `eio-fs-crunch` binary walks a directory tree and writes an OCaml module
holding every directory, file and symbolic link in it, as
[ocaml-crunch](https://github.com/mirage/ocaml-crunch) does. With `-o
assets.ml` it writes the module there and its interface to `assets.mli`;
without, it prints the module alone. A dune rule regenerates the module when
the asset directory changes, and a library stanza compiles it:

```
(rule
 (targets assets.ml assets.mli)
 (deps
  (source_tree static))
 (action
  (run %{bin:eio-fs-crunch} -o assets.ml static)))

(library
 (name assets)
 (modules assets)
 (libraries eio-fs eio))
```

The generated `assets.ml` holds the tree as a value of type `Eio_fs.Crunch.t`.
You never write these entries by hand:

```
(* Generated by eio-fs-crunch. Do not edit. *)

let entries : Eio_fs.Crunch.t =
  Eio_fs.Crunch.
    [
      Dir { path = "/"; perm = 0o755 };
      File
        {
          path = "/index.html";
          perm = 0o644;
          contents = "<h1>Hello from the image</h1>\n";
        };
    ]

let load () = Eio_fs.Crunch.load entries
```

At run time, `Assets.load ()` rebuilds the tree in a new in-memory filesystem
and returns its root. A unikernel or a test with no real filesystem can then read
its static assets through an ordinary `Eio.Path`. This repository crunches
[examples/readme/static](examples/readme/static) with the rule above, and the
example below runs against the module it generates:

```ocaml
Eio_main.run @@ fun _env ->
let fs = Assets.load () in
assert (
  Eio.Path.load Eio.Path.(fs / "index.html") = "<h1>Hello from the image</h1>\n")
```

## Provenance

This code started as Patrick Ferris's
[eio_mem](https://tangled.org/patrick.sirref.org/eio_mem), which was derived
from the Eio filesystem interfaces. The lexical path handling in
`eio-fs.path` is a POSIX-only modification of
[fpath](https://github.com/dbuenzli/fpath). All three are under the ISC
licence; see [LICENSE.md](LICENSE.md).
